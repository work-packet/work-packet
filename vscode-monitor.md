# Upstream task — Show Claude and Codex sessions from Web VS Code on the packet dashboard

Implement this feature in **work-packet**. A packet owner can already follow a scheduled step on the board. They also launch Claude Code and Codex interactively in a packet’s Web VS Code window, sometimes in an extension and sometimes in an integrated terminal. They want to see which sessions belong to each packet, how recently each one did work, and roughly what it was doing. A read-only view covers the request.

## What the owner should see

- Add a **VS Code sessions** section to the packet page and an entry on the board Overview for recent sessions across packets. Use the board’s existing live-refresh behavior. Show the most recently active sessions first and link each to its project or packet.
- Give each session its own row with the harness, a short session identifier, model, last activity time, and reported token usage. Show the LSF job ID and host when the session has a confirmed association with that editor job. Two conversations in one editor should have two rows.
- Add one short **last event** per row. Examples include “Read requested,” “Shell command requested,” “Asked for input,” and “Turn finished.” Derive these from structured events. Report waiting or completion only when the harness supplies that signal. An idle editor, a closed browser tab, and a finished turn each tell us something different. Display a missing model or usage as “unreported.”

## Implementation starting points

The downstream checkout was inspected at upstream commit `a6e2fff`. Check current upstream before editing. The AMD checkout also carries `u20-ide-mtls.patch` for its LSF transport. Keep this feature usable with both board-hosted and job-hosted editors.

1. **Capture the association at Open in VS Code.** In `src/work_packet/ide.py`, the resolved `Open` already has the project, WPID and target. The open handler in `dash/app.py` currently passes only the path and size to `dash/ide.py::Backends.register`. Carry the known identity through the editor launch. Existing workspace settings deliver `WPK_PROJECT` and `WPK_WPID` to integrated terminals. Check the extension host separately because terminal settings cover only the terminal. A single editor target can be reopened from multiple packets or receive a new job after the old one ends.
2. **Bind a harness session ID to the correct launch.** Prefer an explicit session-start event or another verifiable link between the harness session and the editor instance. Collect on the execution host when needed and publish allowlisted metadata through the owner’s private shared state. The board and an LSF job can be on different machines. A transcript’s VS Code client marker proves the kind of client. A matching working directory proves only a workspace match. Label any fallback match accordingly, leave ambiguous packet/job fields empty, and omit unrelated personal sessions. Use `layout.py` for both legacy `packets/<wpid>` and current `.work-packet/runs/<wpid>` layouts.
3. **Normalize native interactive events.** Existing step harness adapters and the downstream spend scanner are useful references. Account for these observed interactive formats and verify against the supported harness versions:
   - Claude JSONL can include `sessionId`, `entrypoint`, `cwd`, `timestamp`, and assistant `message.id/model/usage`. Repeated assistant messages may revise usage for the same message ID. Count each logical message once. A tool-use block’s name can identify an action without its arguments.
   - Codex rollouts can include `session_meta.payload.source = "vscode"` even when `originator` says `codex-tui`. Use session metadata for identity, `turn_context` for model, and task/turn events for progress. Observed usage formats include `token_usage_record.payload.thread_token_usage` and `event_msg/token_count`, which can have null `info`. Prefer a reported cumulative total where available. Avoid adding cumulative snapshots together or counting both formats for one response.
4. **Keep observation cheap and private.** Refresh incrementally outside the dashboard request path, bound reads and retention, and tolerate missing, truncated or rotated records. Reconnects and board restarts should retain session identity and counts. Gate both the panel and any data route on the board owner. Persist and render only identifiers, activity categories, timestamps and usage metadata. Exclude prompts, replies, tool arguments and output, credentials and raw transcripts. Keep interactive usage separate from the scheduled-step ledger. Monitoring must work without a budget provider, a model call, or an additional network listener.

## Acceptance and handback

- Exercise both harnesses through a Web VS Code extension or terminal, and cover both launch paths. Append events while the board is open. Verify that the right packet row updates with the model, last event and tokens, including when a harness omits usage.
- Test two packets sharing a checkout, two sessions in one editor, an unrelated CLI session in the same directory, a scheduled step, and a session resumed after a restart. Verify attribution and token counts. Plant sentinel text in prompts and tool arguments and assert it never reaches the view or metadata store. Check another signed-in user cannot fetch the data directly.
- Cover the local and batch IDE backends with fixtures. For the downstream smoke test, open a packet in an LSF-hosted editor, start a session, observe an update, restart the board, and verify that the same session is still associated with the same live job.
- Return the upstream commit or patch, the dashboard navigation, any required configuration, and test results. Identify which harness/launch combinations provide confirmed attribution and which offer only a workspace match. Downstream can then update its dependency and verify the feature on the farm.
